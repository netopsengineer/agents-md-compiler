# Rendered bundle format version 1

Frozen public contract. Rendered output is byte-exact. A change to any byte
described here is a format change and requires a new `format` value, updated
documentation, explicit golden-diff review, migration and rollback analysis, a
release note, and full integration plus active prompt verification. Never
regenerate a golden file to make a test pass.

## Lock file bytes

The lock is the pinning artifact, and the rendered output records its digest, so
the lock's own serialization is part of this format.

```json
{
  "bundle_id": "example-global",
  "format_version": 1,
  "manifest_sha256": "MANIFEST_SHA256",
  "modules": [
    {
      "id": "core",
      "resolved_source": "/absolute/source/path.md",
      "sha256": "MODULE_SHA256",
      "size_bytes": 2561
    }
  ]
}
```

`MANIFEST_SHA256` and `MODULE_SHA256` are metasyntactic tokens in this document
only. Each is a computed lowercase 64-character hexadecimal digest. Never emit a
token literally.

Serialization rules, all mandatory:

- object keys sorted lexicographically at every depth;
- two-space indentation;
- ASCII-escaped output, so a non-ASCII character in a resolved path appears as a
  `\uXXXX` escape and the file is unambiguously valid UTF-8 regardless of the
  host's filename encoding;
- LF line endings;
- exactly one final LF;
- `modules` preserves manifest order even though object keys are sorted, because
  order is semantic;
- `manifest_sha256` is the digest of the exact manifest file bytes;
- `size_bytes` is the canonical source's base-10 byte count;
- `format_version` is the integer `1`.

The lock never contains source content, only identity. `lock` writes the complete
lock atomically or writes nothing.

## Rendered output bytes

```markdown
# Global Agent Instructions

<!-- agents-md-compiler:generated format=1 -->
<!-- bundle-id: example-global -->
<!-- manifest-sha256: MANIFEST_SHA256 -->
<!-- lock-sha256: LOCK_SHA256 -->
<!-- Do not edit this file. Edit canonical sources and regenerate it. -->

<!-- agents-md-compiler:module-begin id=core sha256=MODULE_SHA256 bytes=SIZE_BYTES -->
# Core Policy

Canonical source bytes continue here.
<!-- agents-md-compiler:module-end id=core -->
```

`MANIFEST_SHA256`, `LOCK_SHA256`, `MODULE_SHA256`, and `SIZE_BYTES` are
metasyntactic tokens in this document only.

### Exact construction

Output is the concatenation of one header block followed by one block per module,
in manifest order. Every line ends with a single LF.

Header block, seven lines exactly:

```text
# Global Agent Instructions
<empty line>
<!-- agents-md-compiler:generated format=1 -->
<!-- bundle-id: {bundle_id} -->
<!-- manifest-sha256: {manifest_sha256} -->
<!-- lock-sha256: {lock_sha256} -->
<!-- Do not edit this file. Edit canonical sources and regenerate it. -->
```

Module block, for each module in order:

```text
<empty line>
<!-- agents-md-compiler:module-begin id={id} sha256={sha256} bytes={size_bytes} -->
{exact canonical source bytes, which already end with exactly one LF}
<!-- agents-md-compiler:module-end id={id} -->
```

Consequences that are part of the contract:

- the file's first byte is `#` and its last byte is LF;
- exactly one empty line precedes each `module-begin` line, including the first;
- no empty line is inserted between a module's content and its `module-end` line,
  because the source's own mandatory final LF already terminates that line;
- the file ends immediately after the final `module-end` line and its LF, with no
  trailing empty line.

### Marker grammar

```text
<!-- agents-md-compiler:generated format=1 -->
<!-- agents-md-compiler:module-begin id=IDENT sha256=HEX64 bytes=DIGITS -->
<!-- agents-md-compiler:module-end id=IDENT -->
```

Markers are compiler-owned ASCII with single spaces exactly as shown. `IDENT`
always matches `^[a-z][a-z0-9-]{0,63}$`, `HEX64` is 64 lowercase hexadecimal
characters, and `DIGITS` is a base-10 integer with no sign, no separators, and no
leading zero unless the value is zero, which cannot occur because an empty source
is rejected.

Identifiers are validated before they reach a marker. The renderer never escapes
an identifier; it refuses to render an invalid one. Any source containing the
prefix `<!-- agents-md-compiler:` anywhere in its bytes is rejected, so a
canonical source can never forge, terminate, or nest a marker.

## What rendered output never contains

- a timestamp, date, or clock reading;
- a host name, user name, process ID, or random value;
- a temporary path or the process working directory;
- an absolute source path;
- the compiler's package version.

All of those belong in the install receipt, which is an operational record rather
than deterministic compiler output. Excluding them is what makes a routine tool
upgrade or a machine path change leave policy bytes untouched when the format,
manifest, lock, and modules are otherwise identical.

## The lock digest inside the output

`lock-sha256` is the SHA-256 of the canonical serialized lock bytes described
above, computed from the same validated byte snapshot used for rendering. It is
not read from whatever happens to be on disk.

This makes `render` and `render --locked` produce identical bytes whenever the
sources match the lock. `--locked` adds an assertion, not a different rendering:
the on-disk lock bytes must equal the freshly serialized lock bytes, otherwise the
state is `LOCK_STALE` and nothing is rendered.

## Determinism

Given identical manifest bytes, identical lock bytes, format version 1, and
identical source bytes, output bytes are identical. Manifest order is output
order. Rendering never consults directory enumeration order, environment
variables, or locale. Rendering twice from unchanged inputs is byte-identical.

## Output self-validation

After rendering, the compiler structurally parses the bytes rather than
pattern-matching them:

1. The seven header lines must match exactly, including the declared format value.
2. For each locked module in order: one empty line, one `module-begin` line whose
   `id`, `sha256`, and `bytes` equal the lock's values, exactly `size_bytes` bytes
   of content, then one matching `module-end` line.
3. The content bytes' SHA-256 must equal the locked digest.
4. Nothing may follow the final `module-end` line and its LF.

This proves each locked source range appears exactly once, in order, with its
recorded identity. A substring search would not: a short module's bytes can occur
inside a longer module's text, so counting occurrences is not a proof.

When reading an existing target, the compiler checks the exact generated header in
the header position and hashes the complete file. A recognized format-1 header
makes the target managed. The target is `CURRENT` only when its whole-file SHA-256
equals the freshly rendered bundle's digest; any other managed target is `DRIFTED`.
Target inspection does not repeat the structural parse because byte equality with
the self-validated fresh render proves the complete structure for `CURRENT`.

## Managed and unmanaged targets

A target is *managed* when its first non-empty marker line is
`<!-- agents-md-compiler:generated format=1 -->` in the exact header position
above. Any other existing file is *unmanaged*, including a hand-written
`AGENTS.md` and a file generated by a different tool.

- managed and byte-identical to a fresh locked render: `CURRENT`
- managed but different: `DRIFTED`
- absent: `MISSING`
- present without a recognized generated header: `UNMANAGED_TARGET`

An unrecognized `format=` value in an otherwise well-formed generated header is
reported as `UNMANAGED_TARGET` rather than `DRIFTED`, because a future format is
not something this version may claim to own or safely overwrite.
